# P11 — Operational Runtime & Multi-Project Bootstrap

P11 permanece em andamento. O MVP permanece **DONE**; esta entrega não reabre
o MVP nem altera a classificação histórica de B-P4-001/TD-P4-001.
P11.1 = **DONE**. P11.2 = **IMPLEMENTED / VALIDATED**. P11.3 = **FUTURE**.

## P11.1 — Operational Project Registry & Dynamic Development Cycles

Estado: **DONE**, aprovado pelo Planner e mergeado na main; implementado e
validado em 2026-10-08, Linux/Docker (`golang:1.25`).

A composição explícita `OperationalDevelopmentService` usa o registry existente
`composition.Config.Projects/Routes`, acrescentando `ProjectConfig.Development`
com `CandidatePolicy`, `PolicyVersion` e `BranchPrefix` trusted. A validação
rejeita projetos/rotas duplicados, rotas desconhecidas, grants órfãos, paths
ambíguos ou sobrepostos e policies inválidas antes de provisionar ciclos.
Os campos de configuração específicos do fluxo READ não são requisitos deste
runtime; MCP não é aceito na composição operacional.

Cada solicitação autenticada recebe 128 bits aleatórios gerados pelo runtime,
um `TaskID` derivado, uma correlação e uma branch sob o prefixo configurado.
Nada disso é derivado do intent. Cada ciclo mantém seu `DevelopmentCycle`,
TaskRepository, CandidateContext, store e workspace próprios. O prefixo termina
em `/`, e a branch final é validada como `GitBranchName`, sempre diferente de
`main`. IDs, rota, Principal, identidade da configuração e receipts são
persistidos antes/depois das operações.

As confirmações exigem a identidade exata do review e são resolvidas pela rota
trusted e pelo Principal autenticado. Existe no máximo um ciclo ativo por
Principal + rota, além de `MaxActive` global. A serialização das solicitações
e o `flock` mantido pela instância garantem single-writer. `MaxCycles` limita
o histórico, inclusive após restart; o snapshot operacional tem limite de 4 MiB.

`ActorEvidence -> ActorAuthenticationPort -> Principal` permanece obrigatório.
Grants continuam exatos por Principal + ProjectID + OperationKind. Nenhum
grant é criado pela rota. `WRITE_APPLY`, `GIT_BRANCH` e `GIT_COMMIT` continuam
três reviews e gates independentes com `ApprovalIssuer` e stores existentes.
Planner/CandidateGenerator continuam usando os adapters Codex tool-free;
recebem dados, sem store, applier, aprovação, callbacks WRITE ou Git.

## Configuração e consulta

O modo piloto permanece disponível. O novo modo é selecionado explicitamente:

```sh
go run ./cmd/development --operational --config /path/operational.json --check-config
```

O exemplo sem credenciais está em
`internal/composition/testdata/operational-development.example.json`. IDs Discord
nesse arquivo são placeholders. Os diretórios devem existir no Linux, ser
canônicos, privados (`0700`), pertencer ao usuário do runtime e não se sobrepor
entre si ou ao runtime-auth. `Workspace` é o diretório trusted sob o qual cada
ciclo provisiona seu workspace e repositório gerenciados; não importa um clone.

`/develop` cria a proposta; `/develop-confirm identity:<review>` confirma uma
operação; `/develop-cancel` bloqueia o ciclo do Principal na rota. A resposta
inclui `Ciclo: <correlação>`. `/develop-status cycle:<correlação>` consulta o
receipt persistido, exigindo a mesma rota e o mesmo Principal. Uma correlação
fornecida para consulta nunca seleciona outro projeto nem concede autoridade.

## Restart e recovery

O runtime aceita roots já utilizados. Receipts terminais `DONE` e `BLOCKED`
continuam consultáveis. Ciclos não terminais viram `BLOCKED` com
`RECOVERY_REQUIRED`, sem review e sem ciclo ativo. Não há reabertura de stores
de efeitos, reemissão/reuso de aprovação, Planner, WRITE ou Git durante restart.
Tasks com transição existente para `BLOCKED` usam o WorkflowEngine. Tasks
interrompidas antes de análise preservam seu estado original porque o domínio
não oferece essa transição; seu ciclo operacional fica explicitamente bloqueado.

Snapshots operacionais interrompidos são preservados em
`operational.recovery-<id>` e nunca adotados como autoridade. Apenas o snapshot
committed é usado, e seus ciclos não terminais ficam bloqueados. Configuração
de projeto diferente da persistida, snapshot committed inválido ou persistência
de Task inconsistente impedem startup e exigem reconciliação humana. A intenção
gravada antes de cada operação impede replay de efeitos cujo resultado ficou
ambíguo. Não existe auto-resume ou nova autoridade de recovery.

## Limitações preservadas

- Policies enumeram arquivos literais; não há glob, `**` ou acesso irrestrito.
- Workspaces começam provisionados vazios; importar clones, seed de arquivos e
  retomada de workspaces existentes não fazem parte desta entrega. InputTargets
  continuam sob o contrato existente e falham fechados se o input não existir.
- Requests são serializadas; vários ciclos podem aguardar review isoladamente.
- Limites existentes de persistência/apresentação do DevelopmentService continuam
  fail-closed para proposals grandes. Não há paginação de reviews.
- Não há garbage collection automática do histórico, workspaces ou evidência de
  recovery. Ao atingir limites, o runtime retorna BUSY ou bloqueia persistência.
- Recovery ambíguo exige intervenção humana; nenhum efeito é retomado.

MCP e P6 permanecem READ-only; legacy P4 e P10.5/P10.6 não mudam. Não foram
adicionados push, PR, merge, MCP WRITE, Windows service ou lifecycle unificado
na entrega P11.1.

## P11.2 — Unified Operational Lifecycle

Estado: **IMPLEMENTED / VALIDATED**, 2026-10-08. MVP permanece **DONE**.

O launcher Windows/PowerShell 7 gerencia três componentes separados: MCP
READ-only em Compose, Development operacional em outro projeto Compose e
Secure MCP Tunnel como processo separado no host. `mcp-runtime.ps1 -Managed`
reutiliza integralmente o build, volumes externos, provisionamento de security
e state e `/readyz` do launcher existente. O modo foreground anterior permanece
disponível. O helper Docker bounded foi extraído para `runtime-docker.ps1`.

Development usa `--operational` e o registry/configuração P11.1 existente.
Planner/Candidate continuam sendo criados pelo runtime existente sob demanda;
o launcher não cria daemon Planner, ciclos, approvals ou autoridade de domínio.
MCP não recebe socket Docker nem ferramentas WRITE. Somente Development mantém
o acesso infraestrutural ao daemon, como na composição P6 existente.

### Preparação e comandos

Requisitos: Windows, PowerShell 7, Docker com containers Linux e Compose,
executável Tunnel já instalado, configurações externas válidas e credenciais
externas. Não há instalação global nem configuração automática de login.
O manifest não secreto de exemplo é `deploy/lifecycle.example.json`; copie-o
para `.runtime/lifecycle.json` e ajuste os paths absolutos. Os campos apontam
para as configurações MCP/Development existentes, workspace READ, fonte security,
token Discord externo, executável Tunnel, porta loopback MCP e volumes Linux.
Não coloque conteúdo de credenciais no manifest.

`DevelopmentVolume` e `RuntimeAuthVolume` devem existir e estar provisionados.
Os roots canônicos privados (`0700`, uid do runtime) usados pelo registry
operacional e ScratchRoot ficam sob `/development`, em diretórios distintos do
volume Development. A configuração continua enumerando projetos e rotas uma
única vez. O volume runtime-auth mantém o contrato P6.4 existente e o login
isolado; o launcher não importa auth de desktop nem lê seu conteúdo. A imagem
Development prepara o diretório pai runtime-auth com modo `0700`.
O token Discord é montado como `/run/secrets/discord_token`, read-only.
Nenhum comando registra automaticamente comandos Discord.

Defina externamente `CONTROL_PLANE_API_KEY`, `MCP_CLIENT_TOKEN` e
`CONTROL_PLANE_TUNNEL_ID`. Então, no clone normal:

```powershell
pwsh -NoProfile -File .\scripts\start.ps1
pwsh -NoProfile -File .\scripts\status.ps1
pwsh -NoProfile -File .\scripts\stop.ps1
# Manifest externo alternativo:
pwsh -NoProfile -File .\scripts\start.ps1 -Manifest C:\private\lifecycle.json
```

`start` retorna controle ao terminal após `READY`; não exige terminais mantidos
abertos. Não são executados comandos LIVE durante a validação desta entrega.

### Transação, estados e readiness

Estados externos: `STOPPED`, `STARTING`, `READY`, `DEGRADED`, `STOPPING`,
`FAILED`. A transação é serializada por um handle de arquivo exclusivo mantido
durante start/stop. Um segundo comando concorrente é rejeitado. Antes de criar
componentes operacionais, valida paths/reparse, secrets por presença/tamanho,
Docker Linux, volumes existentes, disponibilidade da porta e configuração
Development pelo `--check-config` offline existente. O check usa um container
efêmero sem gateway ou providers; build/check são efeitos preparatórios bounded.
MCP também mantém suas validações existentes antes do provisionamento.

A ordem é `STARTING -> MCP -> MCP /readyz -> Development -> readiness
Development -> Tunnel -> aggregate -> READY`. Intenção de cada componente é
persistida antes de iniciá-lo. O listener Development é opcional, restrito a
`127.0.0.1`, sem callbacks do domínio, e só é iniciado depois de `g.Open` e da
composição operacional. Ele fecha no shutdown. O healthcheck interno consulta
`/readyz`; não há porta Development publicada no host nem parsing de stdout.
O Tunnel deve permanecer vivo durante cinco segundos bounded; isso comprova
liveness inicial, não uma sessão remota E2E (P11.3).

Erro/interrupção durante startup executa `finally`, persiste `FAILED` e faz
rollback em ordem inversa, limitado aos recursos owned da tentativa. Cada stop
de container solicita SIGTERM com 35 segundos e tem limite externo de 45
segundos. O launcher MCP anterior conserva seus próprios limites. O rollback
tenta todos os componentes mesmo se um shutdown falhar. Falha de shutdown é
reportada sem declarar sucesso.

### Metadata e ownership

Metadata operacional fica em `.runtime/lifecycle/owner.bin`: versão, instance
ID aleatório de 128 bits, estado, porta, intenções, IDs completos dos containers,
projetos Compose, PID/horário de início/executável do Tunnel. É protegida por
DPAPI CurrentUser com vínculo ao path do clone e gravada por arquivo temporário
exclusivo, flush e rename. O diretório tem ACL privada com herança desabilitada.
Paths reparse/symlink, schemas inválidos/incompletos, tamanho excessivo,
metadata adulterada ou de outro clone/usuário falham fechados.

Containers são verificados por ID imutável e labels exatas de projeto e service,
sob `dev-orchestrator-<instance>-mcp` e `...-development`. Uma intenção durável
permite localizar o container parcialmente iniciado, sempre no projeto aleatório
da tentativa. Um container que substituiu o ID salvo não é adotado nem parado.
O Tunnel exige PID, timestamp de criação e executável iguais; PID isolado nunca
é suficiente. O launcher não encerra processos por nome nem containers genéricos.
O operador Windows que pode executar código como o mesmo usuário continua sendo
trusted; DPAPI não cria uma fronteira contra esse próprio usuário ou administrador.
Metadata é exclusivamente de lifecycle, sem autoridade de domínio.

### Observação e shutdown

`status` só lê metadata e observa identidade/liveness, estado/health dos
containers, `/readyz` MCP e processo Tunnel. Não cria diretórios/locks, não
persiste transições e não repara nada. `READY` exige os três componentes owned
e healthy; perda de componente obrigatório produz `DEGRADED`. Sem recursos
owned vivos, retorna `STOPPED`, inclusive para metadata stale. Metadata inválida
produz `FAILED` e erro, sem efeitos. Uma operação interrompida em STARTING ou
STOPPING exige `stop` antes de novo `start`, sem adoção automática.

`stop` verifica ownership antes de cada encerramento, persiste `STOPPING`,
solicita shutdown normal e persiste `STOPPED` somente após sucesso. Para Tunnel
solicita `CloseMainWindow`, aguarda cinco segundos e usa kill somente do processo
novamente verificado, com mais cinco segundos de limite. Executáveis de console
sem janela podem exigir esse fallback; não há protocolo remoto de shutdown.
Volumes, state, audit, auth e recovery evidence são preservados. Não há `down
-v`, remoção de volumes, prune ou garbage collection. Stop e rollback removem
somente containers owned, inclusive já parados, por ID completo e sem `-v` ou
force, após revalidar ownership e shutdown. Cleanup repetido é idempotente;
identidades Compose por instância e comportamento do Tunnel são preservados.

### Secrets e recovery

Secrets continuam em referências env/arquivos externos. O argv Tunnel contém
`env:CONTROL_PLANE_API_KEY` e `env:MCP_RUNTIME_AUTHORIZATION`, nunca os valores.
Authorization é passado por ambiente só durante spawn e depois restaurado.
stdout/stderr do Tunnel são descartados nos dispositivos NUL, com janela oculta;
raw HTTP logging permanece desabilitado. Saída de provider/Docker e detalhes de
erro são suprimidos pelos comandos operacionais. Nenhum secret é incluído na
metadata, imagem ou Git. O ambiente do shell é restaurado em `finally`.

Restart conserva P11.1: DONE/BLOCKED terminais; ciclos interrompidos ficam
BLOCKED/RECOVERY_REQUIRED. Lifecycle não repete Planner, Candidate, WRITE, Git,
review ou approval e não executa recovery do domínio. MCP permanece READ-only
com as ferramentas existentes. WRITE_APPLY, GIT_BRANCH e GIT_COMMIT continuam
três gates independentes. Não houve mudança nessas composições/contratos.

### Testes e limites

`scripts/test-lifecycle.ps1` usa doubles determinísticos para ordem, duplicidade,
falhas em cada etapa, cancelamento durante readiness, rollback parcial,
observação sem efeitos, stale/foreign owner e concorrência. O teste Windows
`scripts/test-lifecycle-runtime.ps1` cobre DPAPI/ACL/lock, metadata adulterada,
READY incompleto, ID de container substituído e PID reutilizado. O teste Go
cobre loopback readiness, resposta e fechamento. As regressões MCP existentes
e suites P11.1/gates/tool-free/recovery permanecem executadas.
`test-lifecycle-launcher.ps1` exercita o adapter de produção e o script MCP
reutilizado com doubles: happy path, duplicate start, falhas parciais de MCP,
Development/Tunnel, status/stop reais do adapter e ausência de secrets na
metadata/argv controlado. `test-development-runtime.ps1` valida somente o
render offline de Compose, sem iniciar serviço ou usar credencial.

Validação oficial: testes focados e `./scripts/validate.sh` dentro de Linux/Docker
(`go test ./...`, `go vet ./...`, `go build ./...`), `go test -race ./...`, testes
PowerShell e `git diff --check`. As dependências são preparadas antes; os testes
Go rodam com `--network none`. Não há testes que dependam de credenciais reais.

Limitações: preparação inicial dos volumes/config/auth continua explícita;
readiness não certifica operações LIVE, conectividade remota do Tunnel ou
disponibilidade futura de providers. Kill do launcher/host (sem finally) pode
deixar STARTING e componentes owned; `stop` faz a limpeza bounded, sem recovery
automático. Não há heartbeat supervisor, reinício automático, Windows Service,
GUI, instalação, update ou publicação. P11.3 LIVE E2E permanece **FUTURE**.

## Evidência de validação P11.1
